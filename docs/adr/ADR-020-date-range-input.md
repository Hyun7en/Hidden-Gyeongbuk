# ADR-020 · 여행 기간 입력 = 날짜 범위(캘린더)

**상태** Accepted  
**작성일자** 2026-08-09

## 컨텍스트

추천 입력의 기간을 `duration` enum(당일/1박2일/2박3일) 3단계로 받고 있었다. 두 가지 한계가 있었다. (1) 3박4일 이상을 표현할 수 없어 장기 체류 수요를 버린다. (2) **실제 여행 시기를 알 수 없다** — 벚꽃·단풍·축제처럼 경북 관광의 핵심 가치가 계절에 묶여 있는데, 기간만 알고 시기를 모르면 이를 추천에 반영할 수 없다.

## 결정

`duration` enum을 폐기하고 `startDate`·`endDate`(ISO 날짜) 범위를 받는다. 박 수(nights)·일 수(days)·계절은 날짜에서 파생한다. 입력 UI는 날짜 범위 캘린더로 구현한다.

## 근거

① 임의 박 수를 자연스럽게 지원한다 — 3단계 룩업 표를 공식(`Dmax = base × days` 등)으로 일반화하면 된다. ② **계절·축제 가중이 가능해진다** — 이게 진짜 이유다. 시작일의 월로 계절을 판단하고, `festival_detail`의 기간과 직접 겹치는지 계산할 수 있다(추천 알고리즘 §4.7). ③ 날짜 선택은 여행 계획의 자연스러운 사고 단위다.

## 결과

① API `POST /api/courses/recommend` body와 `GET /api/courses` 쿼리가 startDate/endDate로 변경(API v0.8). ② 3단계 제약표(장소 수·거리 상한·숙박)를 공식 기반으로 일반화 — 기존 표는 참고값으로 강등. ③ 날짜 범위는 네이티브 `input type=date`로 표현 불가 → 커스텀 캘린더 컴포넌트 필요(Browser Compatibility §2.9). ④ 공유 URL에 날짜가 담겨 **과거 날짜 링크**가 생길 수 있다 — 차단하지 않고 안내 배너만 표시하기로 잠정 결정(API 명세서 §8). ⑤ **계절 가중은 절반만 동작한다** — 축제 날짜 겹침은 기존 데이터로 계산 가능하지만, "벚꽃·단풍" 같은 계절성 태그가 아직 없다.

## 대안

① enum에 옵션만 추가(3박4일+) — 임의 박 수는 해결되나 여행 시기를 여전히 모르고, 계절 추천이 불가 → 배제. ② 박 수 숫자 입력/스테퍼 — 동일한 이유로 배제. ③ "여행 시기(월/계절)"를 기간과 별도 입력으로 받기 — 계절 추천 목적은 달성하고 UI도 가벼워지지만, 입력이 둘로 나뉘고 일 단위 정밀도(특정 축제와 정확히 겹치는지)를 잃는다 → 날짜 범위로 통합.

## 후속 주석

**2026-08-13** — 결과 ⑤가 말한 계절성 태그는 **ADR-024에서 폐기됐다**. 계절성 태그 체계를 새로 설계하는 것은 자체 어휘를 다시 소유하는 일이라 관광공사 분류 채택과 어긋나기 때문이다. 따라서 계절 반영은 축제 날짜 겹침 하나로 확정됐다 — 절반만 동작하는 상태가 아니라, 근거 있는 항목만 남은 상태다.
