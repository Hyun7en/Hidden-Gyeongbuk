# ADR-017 · 언어 커버리지 판단 = place_translation 조회 (has_en 폐기)

**상태** Accepted (ADR-015의 has_en 존치 결정을 대체)  
**작성일자** 2026-07-30

## 컨텍스트

ADR-015는 `place.has_en`을 "en 번역 존재" 캐시 플래그로 남겼다. 추천 완성도 점수(FR-R, 가중치 10%)가 조인 없이 언어 커버리지를 참조하게 하려는 의도적 비정규화였고, "단일 boolean이라 언어마다 늘지 않는다"는 근거를 들었다. 그러나 ADR-018로 다국어 확장이 확정되면서 이 전제가 무너진다 — 완성도 점수가 답해야 할 질문이 "영문이 있는가"에서 "**사용자 언어**의 콘텐츠가 있는가"로 바뀌기 때문이다. 일본어 사용자에게 영문 유무로 완성도를 매기는 것은 무의미하며, 언어별로 플래그를 두면 `has_ja`·`has_zh_cn`… 으로 컬럼이 늘어 ADR-015가 피하려던 문제가 재발한다.

## 결정

`place.has_en`을 폐기하고, 언어 커버리지는 `place_translation`에 해당 `(place_id, lang)` 행이 존재하는지로 판단한다. 별도 캐시 플래그를 두지 않는다.

## 근거

ADR-007이 세운 원칙 — 실측 근거 없는 최적화는 개발을 제약한다 — 을 그대로 적용한다. `has_en`은 조인 비용에 대한 **측정되지 않은 우려**에서 나온 비정규화다. 현재 데이터 규모는 15곳 기준 수천 건 수준이고 ADR-005에 따라 인메모리 캐시 위에서 추천을 계산하므로, 언어 커버리지 조회가 실제 병목이 될 근거가 없다. 비정규화는 측정 후에 도입해도 늦지 않으며, 반대로 지금 넣으면 다국어 확장 때 반드시 걷어내야 한다.

## 결과

추천 완성도 점수 계산 시 `place_translation`을 함께 조회해야 한다(인메모리 캐시 로딩 시 함께 적재하면 런타임 조인은 발생하지 않는다). `has_en`을 참조하던 코드는 언어 파라미터를 받아 해당 언어 행 존재를 확인하는 방식으로 바뀐다. **성능 측정(ADR-007, WBS P4)에서 언어 커버리지 조회가 병목으로 확인되면**, 언어별 boolean이 아니라 `place.available_langs`(언어 집합 비정규화) 같은 언어 무관 방식으로 재도입한다.

## 대안

① has_en 유지 — 영어만 특별 취급하게 되어 다국어 확장 시 다른 언어 사용자에게 부정확한 완성도 점수를 산출 → 배제. ② 언어별 boolean 컬럼 추가(has_ja, has_zh_cn…) — ADR-015가 피하려던 컬럼 폭발이 그대로 재발 → 배제. ③ `place.available_langs` 집합 컬럼을 지금 도입 — 조인은 피하지만 갱신 시 동기화 부담이 생기고, 무엇보다 필요하다는 측정 근거가 없음 → 측정 후 필요 시 도입하는 것으로 연기.
