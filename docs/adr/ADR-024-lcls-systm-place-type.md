# ADR-024 · 장소 분류 = 관광공사 신분류체계 대분류 채택 (자체 place_tag 폐기)

**상태** Accepted (ADR-014가 예고한 후속 ADR. ERD §9 · 외부 API 연동 설계서 §7의 "분류체계 태그 개편"·"계절성 태그 체계" 해소)  
**작성일자** 2026-08-13

## 컨텍스트

장소 분류축을 두 개 갖고 있었다. `place_type`(자체 7종, contentTypeId에서 파생)과 `place_tag`(자체 6종: 자연·음식·전통·사찰·축제·휴식). 두 축 모두 **어휘를 우리가 소유**한다는 같은 비용을 진다 — 어느 장소를 어느 값에 넣을지 판단하는 규칙을 우리가 만들고 근거를 대야 한다.

그 비용이 실제로 청구된 지점이 `place_tag`다. 부여 규칙이 2026-07-19(ADR-014)부터 "후속 과제"로 남아 미정인 채였고, 그동안 **추천 가중치 35%(관심사 적합도)가 근거 없는 축 위에 예약**돼 있었다. 여기에 계절 가중(추천 알고리즘 §4.7)까지 얹으려면 계절성 태그 체계를 또 우리가 설계해야 했다.

한편 관광공사 신분류체계 코드(`lclsSystm1/2/3`)는 `areaBasedSyncList2` **목록 응답에 함께 온다**. ADR-014에서 "일단 적재만 해둔다"고 결정해 `staging_place`·`place`에 이미 쌓여 있으나 아무 데도 쓰이지 않고 있었다.

## 결정

**(1) `place_type`의 값 체계를 contentTypeId 파생 7종 → `lclsSystm1` 대분류로 교체**한다. 저장 값은 **원본 대분류 코드 그대로**이며 내부 이름으로 재매핑하지 않는다. 단 `C01`(추천코스)은 여행코스(ko=25)에 대응하는 대분류로 place 모델과 맞지 않아 영구 제외되므로(ADR-003/009), 실제 어휘는 **9종**이다 — AC(숙박)·EV(축제/공연/행사)·EX(체험관광)·FD(음식)·HS(역사관광)·LS(레저스포츠)·NA(자연관광)·SH(쇼핑)·VE(문화관광).

**(2) `place_tag` 테이블과 자체 태그 어휘(`PlaceTagType` 6종)를 폐기**한다.

**(3) 관심사(interest)는 별도 축을 두지 않는다.** API의 `interest` enum을 폐기하고, 추천 입력 `interests`는 `placeType`과 같은 어휘를 받는다.

**(4) 계절 태그 가중(추천 알고리즘 §4.7-1)을 폐기**한다. 계절 반영은 `festival_detail` 날짜 겹침(§4.7-2)만 남는다.

**(5) contentTypeId는 수집 대상 선정용으로만** 남는다(어떤 타입을 수집할지). `place_type` 파생에는 쓰지 않는다.

## 근거

① **어휘를 소유하지 않는다.** "하회마을은 전통인가 자연인가"는 우리가 근거를 댈 수 없는 질문이고, 실제로 몇 달간 답하지 못했다. 관광공사 분류는 데이터 제공자가 이미 판정해 실어 보낸 값이라 근거가 외부에 있다.

② **비용이 0이다.** 목록 응답에 함께 오므로 추가 오퍼레이션 호출도, 수작업 라벨링도 없다. 오퍼레이션별 일 1,000건 한도에서 이건 결정적이다.

③ **축이 둘일 이유가 없었다.** `place_type`과 `place_tag`는 실질적으로 같은 질문("이 장소는 무엇인가")에 다른 어휘로 답하고 있었고, 필터 UI에서도 두 셀렉터가 겹쳤다(화면 설계서 S5). 하나로 합치면 API·프론트·추천이 같은 어휘를 공유한다.

④ **정보량이 늘어난다.** contentTypeId가 "관광지(12/76)" 한 덩어리로 뭉개던 것을 대분류는 자연관광(NA)·역사관광(HS)·문화관광(VE)·체험관광(EX)으로 나눠준다. 관심사 매칭의 해상도가 그만큼 올라간다.

⑤ **확장 경로가 있다.** 중·소분류(`lclsSystm2/3`)가 같은 응답에 함께 오므로, 더 깊은 필터가 필요해지면 같은 체계 안에서 내려가면 된다. contentTypeId 7종에는 그 경로가 없다.

⑥ **ADR-007/021과 같은 원칙이다.** 근거 없는 항목에 가중치를 예약해두지 않는다.

## 결과

① **스키마(V3)**: `place_tag` 테이블 삭제. `place.place_type` 값 체계 교체. `place.lcls_systm1/2/3` 컬럼 제거 — 대분류는 `place_type`으로 흡수되고, 중·소분류는 원본이 `staging_place`에 그대로 있으며 Merge는 자유롭게 재실행 가능하므로 필요해질 때 컬럼을 추가하고 재Merge하면 된다(측정 전 비정규화하지 않는다, ADR-007/017).

② **API**: `interest` enum 폐기, `placeType` 어휘 교체, 응답 `tags[]`·필터 `tag` 제거, `meta/options`의 `interests`는 `placeTypes`와 같은 목록을 반환.

③ **추천**: 관심사 적합도(35%)의 근거 데이터가 `place_tag.tag` → `place.place_type`. **산식(코스가 커버한 관심사 종류 비율)과 가중치는 그대로**다.

④ **코드**: `PlaceTagType`·`Interest`·`PlaceTag`·`PlaceTagAssigner` 삭제, `PlaceType` 값 교체. 태그 부여라는 로컬 연산 자체가 사라진다 — 분류는 소스가 주는 값이라 Merge가 그대로 반영한다.

⑤ **프론트**: i18n 라벨 사전 키가 태그 6종 → 대분류 코드. 관심사 셀렉터와 타입 필터가 같은 옵션 목록을 쓴다.

⑥ **재수집 불필요.** `staging_place`에 `lclsSystm`이 이미 적재되므로 Merge 재실행만으로 `place_type`을 채울 수 있다.

⑦ **`lclsSystm1` 결측 대응이 새 리스크다.** `place_type`은 NOT NULL인데 소스가 이 값을 비워 보내면 채울 수 없다. **1:1 대응이 명확한 6개 타입(14→VE, 15→EV, 28→LS, 32→AC, 38→SH, 39→FD)만 contentTypeId로 폴백**하고, **관광지(12/76)는 대분류가 NA·HS·VE·EX 넷으로 갈라져 단일 대응이 없으므로 폴백하지 않고 `QUARANTINED`로 보류**한다(사유: 분류 없음). 오매칭보다 미매칭을 택하는 ADR-016과 같은 결이다. 결측률은 첫 수집에서 실측해 대응을 확정한다.

## 대안

① `place_tag`를 유지하되 `lclsSystm`에서 파생 — 매핑 규칙을 우리가 소유하는 문제가 그대로 남고, 대분류 9종을 6태그로 줄이는 매핑이라 정보만 잃는다 → 배제. ② `place_type`은 contentTypeId 유지 + `place_tag`만 교체 — 축이 둘로 남고, 두 축이 같은 질문에 다른 답을 줄 수 있다(contentTypeId=관광지인데 대분류=음식) → 배제. ③ 대분류 대신 중분류(`lclsSystm2`) 채택 — 선택지가 수십 개가 되어 관심사 UI로 쓸 수 없다 → 대분류를 축으로 쓰고 중·소분류는 향후 세분 필터로.

## 후속 주석

**2026-08-13 (실측)** — 결과 ⑦이 제기한 리스크가 **해소됐다**. 안동 1개 지역을 국·영문으로 수집한 820건(ko 523 / en 297) 중 **`lclsSystm1` 결측은 0건(0.0%)**이고, 폴백이 불가능한 관광지(12/76) 결측도 0건이다. `C01` 유입도 없었다. Merge 결과 quarantine 44건은 **전부 Identity Resolution 실패**(이름 불일치·추출 불가·복수 후보)이고 "분류 없음" 사유는 0건 — 즉 폴백과 분류 quarantine 경로는 실전에서 한 번도 타지 않았다. 안전망으로 유지하되, **표본이 안동 한 곳**이므로 15개 지역 전량 수집 시 재확인한다.

덧붙여, 분류 정확도가 구 방식보다 높다는 증거도 나왔다 — 안동의 "산마루산장·산숲가든·산청갈비·학가산참마식당"은 이름에 "산"이 들어 구 `PlaceTagAssigner`였으면 전부 자연 태그가 붙었을 장소들인데, 관광공사 분류는 이를 정확히 `FD`(음식)로 잡았다. 반대로 `NA`가 13곳으로 적은 것은 누락이 아니라 안동이 역사 도시(`HS` 75곳)라는 실제 성격이다.
