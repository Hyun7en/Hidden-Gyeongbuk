# ADR-012 · DB 스키마 관리 = Flyway 마이그레이션

**상태** Accepted  
**작성일자** 2026-07-16

## 컨텍스트

JPA 엔티티 8개의 스키마를 Hibernate `ddl-auto: update`로 자동 생성·관리해왔다. 이 방식은 스키마 변경 이력이 코드로 남지 않고, 배포 환경에서 예측 불가능한 DDL이 실행될 위험이 있다. 단독 개발이라도 실무 표준에 가까운 방식으로 가기로 함.

## 결정

Hibernate `ddl-auto`를 `validate`로 바꾸고, 스키마는 Flyway 마이그레이션(`db/migration/V1__init_schema.sql`, `V2__seed_hub_region.sql`)으로 버전 관리한다. 이후 엔티티 구조를 바꾸면 새 버전(V3...) 마이그레이션을 추가하고, 이미 적용된 파일은 수정하지 않는다.

## 근거

스키마 변경 이력이 코드로 남아 리뷰·롤백이 가능하고, 여러 환경(로컬/배포)에서 동일한 스키마를 보장할 수 있다. Flyway는 순수 SQL 파일 기반이라 학습 곡선이 낮고 Spring Boot 자동 설정을 지원해 단일 개발자·단일 DB(MySQL) 규모에 적합하다.

## 결과

엔티티만 고치면 재기동 시 자동 반영되던 흐름이 사라지고, 반드시 마이그레이션 SQL을 같이 작성해야 한다. 초기 전환 시 기존 로컬 DB를 초기화(볼륨 재생성)해야 했다.

## 대안

Liquibase — XML/YAML 기반으로 기능은 더 많지만(롤백 자동 생성, 여러 DB 벤더 지원) 단일 DB·단독 개발 규모에는 과함 → Flyway 채택. `ddl-auto: update` 유지 — 학습·설정 부담은 없으나 실무 표준과 거리가 있고 스키마 변경 이력 추적이 불가능 → 배제.

## 후속 주석

**2026-08-12** — "이미 적용된 파일은 수정하지 않는다"는 원칙에 **1회 한정 예외**를 두었다(ADR-023) — 구 V1~V11을 ERD v0.9 기준 새 V1으로 스쿼시. Flyway 채택과 원칙 자체는 그대로 유효하며, 스쿼시 이후의 변경은 다시 증분 V파일로 쌓는다.
