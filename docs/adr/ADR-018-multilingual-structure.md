# ADR-018 · 다국어 확장 = 구조는 N개 언어, 실데이터는 국·영문 우선

**상태** Accepted  
**작성일자** 2026-07-30

## 컨텍스트

TourAPI는 영문 외에 일문·중문(간체/번체) 등 다국어 서비스를 제공하며, 서비스 대상이 외국인 관광객이므로 영어권 외 방문객으로 확장할 실익이 크다. 그러나 공모전 마감(2026-09-21)까지 남은 기간에 전 언어를 실제로 수집·번역·검증하는 것은 현실적이지 않다. 한편 나중에 언어를 추가할 때 스키마·코드를 다시 손봐야 한다면 확장 자체가 무산될 위험이 있다.

## 결정

**구조는 N개 언어를 전제로 설계하되, 실데이터는 국문·영문부터 적재한다.** 언어 추가 시 스키마 변경이나 코드 수정이 발생하지 않는 것을 설계 목표로 삼는다. 이를 위해 네 가지를 규정한다.

**(1) 언어는 행** — 언어별 데이터는 `place_translation` 행으로 저장한다(ADR-015). 언어별 컬럼·불린 플래그를 두지 않는다(ADR-017).

**(2) 언어 소스는 대등** — 특정 언어를 마스터로 삼지 않고 모든 언어 서비스를 독립 수집 후 병합한다(ADR-016).

**(3) 매칭은 언어 중립** — 동일 장소 판정은 좌표를 1순위로 하고, 이름은 추출 가능한 언어에서만 보조로 쓴다.

**(4) 언어 코드는 BCP 47** — `ko`, `en`, `ja`, `zh-CN`, `zh-TW`, `fr`, `de` 등 표준 표기를 쓴다.

또한 언어별 TourAPI 서비스명과 contentTypeId를 **코드가 아닌 데이터**(레지스트리·매핑 테이블)로 보유해, 언어 추가가 행 추가로 끝나게 한다.

## 근거

① 언어 추가 비용을 사전에 0에 가깝게 만들어두면 확장 결정이 일정 압박에 좌우되지 않는다. ② BCP 47은 중국어 간체·번체 구분을 표준으로 흡수하고, 프론트 `lang` 속성·`Accept-Language` 헤더와 그대로 호환되어 변환 계층이 불필요하다. ③ contentTypeId를 데이터로 두면 언어별 분기 코드가 생기지 않는다 — 영문에서 이미 국문과 다른 코드 체계(12→76 등)를 확인했으므로 다른 언어도 같을 것으로 전제하는 편이 안전하다.

## 결과

MVP 범위는 국·영문으로 유지되며 SRS의 Out of Scope("다국어") 표현은 "구조는 다국어 대응, MVP 실데이터는 국·영문"으로 조정해야 한다. 언어 추가 절차는 7단계로 정의된다(외부 API 연동 설계서 §6): 서비스 실측 → 레지스트리 행 추가 → contentTypeId 매핑 행 추가 → staging 수집 → Resolution 재실행 → 번역 백필 → 번역 문자량 한도 재산정. **언어 추가 시 스키마 변경이나 코드 수정이 발생하면 설계 원칙이 깨진 신호**로 보고 원인을 점검한다. 번역 API 무료 한도(월 50만 자)는 언어 수에 비례해 소모되므로 언어 도입 전 재산정이 필요하다.

## 대안

① 지금 전 언어 수집·구현 — 마감 내 완료 불가, 검증 부담 과다 → 배제. ② 영문 전용으로 설계하고 확장은 그때 가서 재설계 — 스키마·수집 파이프라인·조회 폴백을 전부 다시 만들어야 해 확장이 사실상 무산됨 → 배제. ③ 구조는 다국어로 하되 중·일문 실데이터도 지금 일부 적재 — 검증 없는 데이터가 쌓여 품질 문제를 키움 → 국·영문 완성 후로 연기.
